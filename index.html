Savannah, Georgia — building AI tools

I build tools that show their reasoning instead of hiding it.

Fifteen years in illustration and design, then two years reading markets full time. Both taught the same lesson: the useful part of any tool is the part that shows you what it is actually doing. Below are two working systems and the failures that shaped them.

Tools

SignalBrief

Turns a source document into a structured brief that separates what the source supports from what it merely asserts.

Paste in an article, filing, transcript, or set of notes. SignalBrief extracts the consequential claims and labels each one by what the supplied evidence actually establishes — source-supported, inference, opinion, or unsupported. It maps typed dependencies between claims, sorts material information from promotional filler, and answers a thesis you supply with a verdict that includes “insufficient evidence” as a legitimate answer.

The rule the whole tool is built on The label reads “source-supported,” never “fact.” The tool has verified nothing. It reports what the material in front of it does and does not establish, and it says which is which.

A proportional bar above the claims shows the composition of the source at a glance. Run it on a press release and you see immediately how little of it is substantiated. That bar is the product’s argument made visual.

What the tool refuses to do Ask it about dinner recipes while handing it a story about a tech selloff and it stops before analysing anything. It names the subject you gave it, names what the source is actually about, and makes you choose — rather than quietly reinterpreting your question to fit the document in front of it.

Build log

Three versions, each a response to something that broke. The failures are the part worth reading.

  1. One prompt, eight sections, a single API call

    Broke: output truncated mid-table on any real source.

    The token ceiling was invisible until a substantial document hit it. It would have failed live in a demo. Rebuilt as a staged pipeline passing a condensed digest between stages rather than full output.

  2. Staged pipeline, epistemic labels corrected

    Broke: the ceiling moved rather than disappeared.

    One stage still carried too much. Split it further, capped every stage’s output explicitly, and added a repair pass that walks backward through truncated JSON to the last complete value and closes what is open — so a cut-off response yields the four findings that finished writing instead of losing all five.

    The same version fixed a reasoning problem. v0.1 labelled claims “fact,” which implied a verification the tool never performed. Renamed to “source-supported,” and confidence was redefined to measure the strength of the evidence relationship rather than the likelihood of truth.

  3. Runtime maintenance

    Broke: every failure looked identical to the user.

    Ten distinct failure modes were collapsing into one message. Separated them, each with its cause and its remedy, and gated retries so unrecoverable failures stop immediately instead of failing twice as slowly. Added an optional bring-your-own-key mode for local testing, held in memory only and never persisted.

Not yet deployed publicly. A public version needs a server-side proxy holding the API key as an environment secret; the tool documents that architecture rather than pretending the browser-side version is production-ready.

Adaptive Day-Trading Training System

A practice system that makes you commit to a trade decision before it shows you what happened next.

Trading practice is quietly ruined by hindsight. Once you can see the following candles, almost any explanation sounds correct. The system withholds future price action, forces a decision at the historical decision point, and grades the reasoning rather than whether the eventual move happened to be favourable.

Product thesis Judge the decision before revealing the outcome. Price structure is primary evidence; EMA and Fibonacci are secondary confluence.

Before choosing buy, sell, wait, or no trade, the learner has to state an exact entry trigger and an exact invalidation. Structure governs the grade — key levels, reclaim and retest behaviour, trend integrity. Indicators are context, never permission to ignore structure that is still intact.

The case the system is really testing Look at the run into the decision point: a red candle at 9:45 interrupting a green sequence, with the retest low still intact beneath it. Nothing has invalidated. A learner who sells there has been governed by the candle, not by the rule they wrote sixty seconds earlier.

These near-invalidation cases are deliberate. Red candles, long wicks, temporary EMA loss and aggressive pullbacks are included specifically to separate emotional reaction from rule-based decision-making. The lesson being trained is reclaim, retest, hold, confirmation — not price crossed a line, press buy.

What testing changed

The most useful lesson came from an interface failure — and from working out which layer was actually failing.

The first build rendered the quiz inline, inside the chat client itself. The widget kept crashing, and behaviour differed from client to client. Submission and rendering friction was on its way to becoming the entire user experience. The learning logic was sound; the layer it was sitting in was not.

Design lesson The problem was not that the interface was too ambitious. It was that inline rendering inside a chat client could not be relied on. Moving the interface out — into a standalone HTML file the learner taps open — removed the failure without giving up a single feature.

Diagnosing the layer rather than the symptom meant the rebuild could be more capable than the version that broke, not less. The current trainer carries EMA 9, EMA 20, VWAP and Fibonacci levels, each on an independent toggle, and a six-candle replay with a hard stop at the decision point.

Training workflow only — not a brokerage integration, a prediction engine, or an automated trading system. It trains decision quality and does not promise profitable outcomes. Grading can drift if the structural rubric is not kept explicit and stable, which is a real maintenance cost rather than a footnote.

How I work

I don’t write production code. I design what a tool should do, specify how it should behave when things go wrong, test it against real material, and iterate on what breaks. Both systems above were built in conversation with AI — which is the point, not a disclaimer. The skill on display is knowing what to ask for, recognising when the answer is wrong, and diagnosing which layer is actually failing.

Three things I hold to:

  • A tool that can’t say “I don’t know” isn’t trustworthy. Uncertainty gets a label, not a hedge.
  • Failure states are part of the design. Most of the work in both tools is in what happens when something goes wrong.
  • Confidence has to be reproducible. If the same input gives a different rating twice, the rating means nothing.
